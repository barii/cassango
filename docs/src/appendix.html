A. Case study: CustomerNotifications

The SS.RMS.CustomerNotifications service (branch use-cassa) originally stored its data in Cassandra through the scylla driver. It now uses cassango through cassango-client. It shows how Cassandra tables map to cassango collections.

Cassandra featurecassango replacement
Table with a composite primary keyA collection. _id is the old primary key columns joined with | (escaped). Writing the same key again overwrites, exactly as before.
Partition key queriesAn indexed pk or group_key field holding the old partition key. IN on partition keys becomes {pk: {$in: [...]}}.
Clustering order + paging stateA sort_key field: {i64::MAX − millis:019}|{_id}, so ascending order is newest first. The page token is the base64 of the last sort_key; the next page asks for sort_key $gt token.
One column per data typeOne document per (customer, data type), so data types written concurrently don't overwrite each other.
SELECT … GROUP BY alert_typeOne indexed count per alert type, run in parallel; zero counts are dropped.
TTL (2 months)An expires_at field (written + 60 days) and an hourly task running deleteMany({expires_at: {$lt: now}}) on each collection.
LOCAL_QUORUMConsistency::Quorum (cassango has a single data center).

B. Error reference

StatusDriver errorMeaning and what to do
400BadRequestInvalid filter, update operator, document or collection name. Fix the request.
404NotFound / NoneDocument, index or node not found. Missing documents come back as None in the driver.
409ConflictA repair is already running, or a range movement is in progress (decommission, removenode, cleanup). Try again later.
503UnavailableFewer replicas alive than the consistency level needs. Nothing was written. Retry, or use a lower consistency level.
504TimeoutEnough replicas were alive but didn't acknowledge in time. The write may have been applied on some replicas. Retrying a put or delete is safe; retrying an $inc update may apply it twice.

C. Simplifications and limits

cassango is deliberately small. Compared with the real systems:

  • Membership. A fixed-timeout failure detector instead of phi-accrual. Gossip sends the full state, not digests.
  • Storage. Size-tiered compaction only. No block cache (the OS page cache does that job), no compression, no write throttling if flushes fall behind. Values are stored as JSON text, not a binary format like BSON.
  • Hints are kept in memory only, so they're lost if the coordinator restarts. Repair covers that.
  • Repair rescans a replica's whole dataset on every run. There's no incremental repair, and a repair response holds all the entries of the differing leaves at once.
  • Range movements copy from every live replica rather than one source. That keeps the newest data but moves up to RF times as much. Tokens come from the node id, so you can't choose or move them, and there's no "replace a dead node" shortcut: use removenode, then join a fresh node. A removed node that comes back with its old data directory rejoins with stale data, so wipe it first.
  • Queries. find always asks every node (indexes are local, not global). Sorting and limits happen on the coordinator after all matches are gathered. There are no compound indexes and no index-backed sorting.
  • Writes. update is read-modify-write and not atomic under concurrent updaters. updateMany/deleteMany are loops. Inserts are upserts: a duplicate _id overwrites.
  • Security. Client and node-to-node traffic is plain HTTP/JSON with no authentication or TLS. Run it on a trusted network.
  • No databases or namespaces beyond collections, and no transactions.
