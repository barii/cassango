Part II

Developer guide

How cassango works inside: the code layout, how a node is built, and how requests, membership, storage, repair, node moves and indexes work. Read this before you change the code.

10. Repository layout

The repository is a Cargo workspace with two crates. The cassango crate builds two binaries: the server and the shell. The cassango-client crate is the driver library.

11. Inside a node

Every node runs the same code and plays every role. There's no master. A request that arrives at a node is handled by the coordinator layer, which uses gossip and the ring to find the replicas and talks to them, including itself, over the /internal API.

Concurrency model: the HTTP server, gossip, hint replay, repair and streaming are tokio tasks. The storage engine runs a dedicated cassango-storage thread for flushes and compactions, and the index manager a cassango-index thread for builds. Shared state uses parking_lot locks and is never held across an .await.

12. Partitioning: the token ring

Every node owns 16 positions (tokens, or virtual nodes) on a 64-bit ring. The tokens come from hashing the node id, so they're stable across restarts. A document's position is key_token(collection, id): 64-bit FNV-1a followed by a splitmix64 finalizer. The hash is written by hand because it must give the same result in every process and version, which std's hasher doesn't promise.

A TokenRange is (start, end] and may wrap around zero. Ranges are the unit of ownership for repair, streaming and cleanup. ring.rs can list the ranges a node is a replica for, its primary ranges, and the ranges whose owners change between two rings (movement_ranges).

13. Gossip and failure detection

Every second each node increments its own heartbeat and swaps its whole membership table with a peer: a POST to /internal/gossip, whose reply carries the peer's table. Both sides keep, for each node, the entry with the higher version (generation, heartbeat, status_seq). The generation changes on every restart, so a restarted node is never mistaken for an old one. The same message carries the index schema, merged by last write wins.

  • UP/DOWN is local: a node marks a peer DOWN when it hasn't seen a newer heartbeat for --failure-timeout-ms. Coordinators use this to decide which replicas are alive.
  • Status (JOINING, NORMAL, LEAVING, LEFT) is set by the node itself, or by removenode on behalf of a dead node. Each change increments status_seq, so the change wins against older entries everywhere.
  • From the merged table, each node computes the current ring (NORMAL + LEAVING) and the future ring (NORMAL + JOINING). Section 18 explains why there are two.
  • Nodes that become UP again trigger hint replay (next section). LEFT nodes are dropped from gossip targets.

14. The write path

A write (insert, put, update, delete) becomes a Mutation: collection, key, and a Record with the coordinator's timestamp in microseconds and either a JSON value or a tombstone.

  1. The coordinator assigns the timestamp, then asks the ring for the replicas, plus any pending replicas if a node is joining or leaving.
  2. If fewer than the consistency level are alive, it fails with 503 before sending anything.
  3. It sends to all live replicas in parallel, including itself if it's one. A replica applies the batch through storage.apply_batch: commit log, then memtable, plus index upkeep.
  4. It returns once enough current-ring replicas have acknowledged, or 504 after rpc_timeout. The other requests keep running.
  5. Down replicas, and replicas whose request failed, get a hint in the coordinator's memory, up to 100,000 per node. Every 2 seconds the hint replayer delivers hints to nodes that are UP again. Hints for LEFT nodes are dropped.

update runs on the coordinator: a read at the requested consistency, the operators applied by query.rs, then a normal write. It isn't atomic: concurrent updates resolve by last write wins.

15. The read path and read repair

The coordinator asks every live replica, waits for as many answers as the consistency level needs, and returns the version with the newest timestamp. A tombstone means "not found". Replicas that answered with an older version, or with nothing, are sent the winner in the background. That's read repair: it fixes data that gets read. Section 17 covers repair of everything else.

16. Queries: two-phase find

Documents are spread by _id, so a filter on any other field has to ask every node. find runs in two phases so that a stale replica can't return a document that has since been changed or deleted.

  • matched counts all matches. docs is the page after sort, skip and limit, which run on the coordinator.
  • partial: true means some node didn't answer phase 1. LEFT nodes don't count.
  • With explain, each node reports its plan (index or full scan), how many entries it examined, and how many matched.
  • count is a find that returns only matched.

17. The storage engine

Each node stores its data in a log-structured merge tree (LSM), like Cassandra's. Writes are appends and never read old data, except for index upkeep on indexed collections. Reads merge everything and pick the newest timestamp.

Durability

  • Commit log. Segmented. Each record is framed as len | crc32 | json. On startup the log is replayed. A torn or corrupt tail after a crash is detected by length and CRC and skipped. A segment is deleted once every mutation in it is in an SSTable. --fsync fsyncs after every batch. Without it, a crash can lose the last writes the OS hadn't written, which replicas and hints cover.
  • Atomic SSTables. Each SSTable is written to a .tmp file, fsynced, then renamed into place, so a crash never leaves half a table.
  • Graceful shutdown. SIGINT flushes the memtable and stops cleanly.

SSTable format

Keys, merging and compaction

  • Key space. Data keys are <collection>\0<id>. Secondary index entries live in the same tree under a \x01 prefix, which sorts before all data (section 19).
  • Scans stream a k-way merge (merge.rs) over the memtables and every SSTable, keeping the newest version of each key. A node's data doesn't have to fit in memory: only memtables, sparse indexes and bloom filters stay there.
  • Size-tiered compaction groups SSTables of similar size. Once a group reaches --compaction-threshold, it's merged into one table. compact major merges everything.
  • Tombstone purge. A tombstone older than --gc-grace-secs is dropped during compaction, but only if no SSTable outside the compaction and no memtable could still hold an older value for that key. Otherwise the deleted document would come back.
  • Cleanup compaction rewrites SSTables through a KeyFilter that drops keys outside the node's ranges.

18. Anti-entropy repair

Hinted handoff and read repair fix most differences between replicas, but not all. Hints are lost when a coordinator restarts, read repair only touches data that gets read, and a node can lose its disk. Repair compares replicas with Merkle trees and copies only what differs. A run covers the node's primary ranges, like nodetool repair -pr, so running it on every node covers the whole ring once.

  1. Validation. For each primary range, the node asks every replica (/internal/repair/trees) to build a Merkle tree in one scan of its local data. Each range splits into 2depth leaves by token (depth 10 by default, 16 at most). XOR makes a leaf hash independent of entry order. Inner nodes hash their children.
  2. Comparison. Trees are compared from the root down, so only differing leaves come out.
  3. Streaming. All replicas' entries in those leaves, tombstones included, are fetched (/internal/repair/fetch). The newest version of each key wins, and each replica is sent only what it lacks, in batches of 500.

Ranges with a replica down are skipped and listed in the report's errors. Only one repair runs per node at a time: a second request gets 409. --repair-interval-secs schedules repair. Repair must cover every node more often than --gc-grace-secs. Otherwise a replica that missed a delete keeps the old document, and after the tombstone is purged elsewhere, repair copies that document back to the other replicas.

19. Adding and removing nodes

A node moves through four states, carried in gossip:

While data is moving, two rings exist. Reads and acknowledgements use the current ring. Writes also go to the replicas the future ring adds, so the new owner doesn't miss writes made while it copies.

Every move is built from one step, pull: a node copies token ranges from all the live replicas that currently hold them, in pages over /internal/stream, and keeps the newest version of each key. Pulling from every replica, not just one, means one stale replica can't leave the new owner with old data.

OperationWhat happens
JoinA node with an empty data directory starts as JOINING. If it finds an existing cluster, it waits --ring-delay-ms so every node starts sending it writes, pulls the ranges it will own, then turns NORMAL. A bootstrapped marker file stops it from doing this twice.
DecommissionPOST /admin/decommission on the leaving node. It turns LEAVING, each new owner pulls the ranges it gains (/internal/pull), then the node turns LEFT. If a pull fails, it goes back to NORMAL.
RemovenodeFor a node that is DOWN for good. The dead node is marked LEAVING on its behalf, so writes go to the new owners. They pull from the surviving replicas, then the dead node is marked LEFT.
CleanupAfter a join, the old owners still hold data they gave away. Cleanup rewrites their SSTables without it, including index entries for those documents. It refuses (409) while any node is joining or leaving.

Only one range movement can run at a time in the cluster: decommission and removenode refuse with 409 while another node is joining or leaving.

20. Secondary indexes

Indexes are local, as in Cassandra: each node indexes only the documents it stores. find still asks every node, but each node reads index entries instead of scanning the collection.

  • Exact maintenance. Every local write to an indexed collection goes through apply_batch, whether it comes from a client, a hint, repair or a join. Under index_write_lock the node reads the document's current winning version. If the incoming write wins, it writes tombstones for the old version's entries and live entries for the new one, at the new version's timestamp. A late, older write leaves the index alone.
  • Verified results. Every document an index finds is re-checked against the full filter, so an index can narrow the search but never change the answer.
  • Schema. Definitions travel in gossip, merged by last write wins, and are saved in schema.json. A node starts maintaining a new index on every write at once, backfills existing documents in the background, and only uses the index once that's done. A node that was down when an index was created builds it when it comes back. A dropped index stops being used at once, and its entries are removed later by compaction.
  • Local only. Index entries never appear in repair trees, streams or stats. Each node rebuilds its own.

21. Inside cassango-cli

  • main.rs: flags, the REPL loop with history and multi-line input, script mode, exit codes, shell commands (help, show, consistency, …).
  • parse.rs: turns db.<c>.<method>(args) chains such as .sort().limit().consistency() into a Command. JSON5 arguments make {age: 31} work. is_complete decides when a multi-line statement is finished.
  • client.rs: one HTTP client over the public API. It tries hosts in order on connection errors.
  • output.rs: pretty JSON, aligned tables (columns are the union of document keys, _id first), or JSON Lines.

22. Inside cassango-client

  • lib.rs: Client and ClientBuilder, request sending with failover, cluster(), ping(), refresh_hosts().
  • collection.rs: Collection<T> and the Find<T> builder, which implements IntoFuture so a chain can be awaited directly. insert_many, update_many and delete_many run up to 16 requests at a time with owned data, so their futures are Send and work with tokio::spawn.
  • query.rs: Filter, Update, Order. Builders turn into serde_json::Value, and everything that takes a filter also takes plain JSON (impl Into<Value>).
  • types.rs: FindResult, ClusterInfo, Member, IndexInfo, Replica, NodeInfo.
  • error.rs: the Error enum, status mapping and is_retryable().

Conventions

  • Never hold a lock across .await. Move blocking storage work to the storage thread or spawn_blocking.
  • Every write that reaches a replica must go through apply_batch, or index maintenance breaks.
  • Changing the SSTable or commit log format needs a version bump: the footer carries version and magic.
  • Node-to-node endpoints live under /internal and aren't part of the public API.
